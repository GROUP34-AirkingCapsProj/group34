## 0. Context & Decisions

### What exists today (Stage-1 findings)

The current `backupV3` branch enforces access **entirely through route middleware** — there is **no** `permissions` table, no `role_permissions`, no per-user overrides, no Gates, and no Policies.

- **Roles:** `roles` table (created via the SQL dump, *no migration*), seeded by `RolesAndBranchesSeeder` with `firstOrCreate` in a fixed order:
  - **SA** = `admin` = `role_id 1`
  - **IA** = `inventory_analyst` = `role_id 2`
  - **BM** = `branch_manager` = `role_id 3`
  - **WP** = `warehouse_personnel` = `role_id 4`
  - **AU** = `auditor` = `role_id 5`
- **`users`** columns: `user_id` (PK), first/last name, email, username, `password_hash`, phone, **`role_id`** (int FK), `location_id`, `status_id`, otp fields, soft-deletes.
- **Enforcement:** the variadic `role` middleware (`App\Http\Middleware\CheckRole`) compares `user->role->role_name` against a **hardcoded list baked into each route** — used **74 times** in `routes/api.php` (e.g. `role:admin,inventory_analyst`).
- **`auditor.readonly`** (`App\Http\Middleware\AuditorReadOnly`) is **global** in the `auth:sanctum` group: it blocks every non-GET request for the auditor role (except logout/refresh/user). This is a hard stop, stricter than any grant.
- **Other middleware:** `location.scope`, `branch`, `extend.sanctum.session`, `auth.query.token`, `log.activity`.
- **Audit infra present:** `audit_trail` table + `AuditTrail` model (generic old/new JSON diffs) and an `Auditable` trait — *reused conceptually but kept separate from the new permission-specific log.*
- **Frontend:** React (not Blade). `frontend/src/admin/utils/roles.js` holds a hardcoded `ROUTE_ACCESS` map + `canAccessRoute()` and per-role menus. `RolePermissions.jsx` already exists but is a **static display stub** (its "Manage Permissions" button only `console.log`s).

### Locked decisions

| # | Decision |
|---|---|
| Enforcement model | **Build DB tables + resolver + seeders + SA management UI + audit log now. Migrate the 74 `role:` routes to the new `permission:` middleware in a later phase (Phase 2).** |
| Source of truth | **DB tables are canonical.** The seeder populates defaults once from the matrix below; SA edits them live via the UI thereafter. |
| Matrix vs. code conflicts | **Reconciled before seeding** (see §7). Five themes decided by the user. |

### Reconciliation decisions (applied to the seed matrix in §8)

- **Theme A — Auditor write grants:** the supplied matrix grants AU write access on several features (supplier, item-supplier mapping, PO creation, delivery receiving, report `create`). **Seed all AU write cells as `0`.** `auditor.readonly` remains the hard outer guard. AU *read* grants are preserved.
- **Theme B — `archive` action:** **seed `archive` as SA-only for every feature** (matches "destroy is admin-only" in live code). *Note: this deliberately tightens `category_management` / `brand_management` / `uom_management`, where live routes currently let IA delete — see §7.*
- **Theme C — `inventory_transfers.approve`:** **SA, IA only** (keeps separation-of-duties; matrix's BM/WP grants dropped).
- **Theme D — `pos_sales_recording.create`:** **SA, BM, WP** (seed the matrix as-given).
- **Theme E — `purchase_order_creation` write actions:** **SA, IA only** (AU dropped per Theme A; `archive` SA-only per Theme B; `read` keeps AU because the live PO index is unguarded and auditors view POs today).

## 1. Database Design

Four new migrations. `roles` and `users` are untouched.

### a. `permissions` — catalog of every feature+action

| column | type | notes |
|---|---|---|
| `permission_id` | BIGINT UNSIGNED, PK, AI | |
| `feature` | VARCHAR(64) | e.g. `barcode_inventory_processing` |
| `action` | ENUM('create','read','update','archive','approve') | |
| `description` | VARCHAR(255) | human-readable |
| `created_at` / `updated_at` | TIMESTAMP | |

- **Unique index** on `(feature, action)`.
- Rows are generated by the seeder from the canonical matrix (§8) — only the `(feature, action)` pairs that actually appear in the matrix get a row (e.g. dashboard features get only a `read` row).

### b. `role_permissions` — default grant per role

| column | type | notes |
|---|---|---|
| `role_id` | BIGINT UNSIGNED, references `roles.role_id` (no hard FK — matches project convention) | |
| `permission_id` | BIGINT UNSIGNED, FK → `permissions.permission_id`, ON DELETE CASCADE | |
| `is_granted` | BOOLEAN, default `0` | |
| `created_at` / `updated_at` | TIMESTAMP | |

- **Surrogate `id` PK** + **UNIQUE `(role_id, permission_id)`** (a surrogate PK keeps Eloquent `updateOrCreate` UPDATEs safe; a composite PK would break them).
- Seeded once from §8; SA edits live via the UI (DB remains truth).

### c. `user_permission_overrides` — per-user override (always wins)

| column | type | notes |
|---|---|---|
| `override_id` | BIGINT UNSIGNED, PK, AI | |
| `user_id` | BIGINT UNSIGNED, FK → `users.user_id`, ON DELETE CASCADE | |
| `permission_id` | BIGINT UNSIGNED, FK → `permissions.permission_id`, ON DELETE CASCADE | |
| `is_granted` | BOOLEAN | the override value |
| `granted_by` | BIGINT UNSIGNED, FK → `users.user_id` | the SA who set it |
| `granted_at` | TIMESTAMP | |
| `revoked_at` | TIMESTAMP NULL | **NULL = active** |
| `reason` | TEXT NULL | |
| `created_at` / `updated_at` | TIMESTAMP | |

- **Index** `(user_id, permission_id, revoked_at)`.
- Active override = `revoked_at IS NULL`. "Reset to role default" **revokes** (sets `revoked_at`) rather than deleting, preserving history.
- At most one active override per `(user_id, permission_id)` — enforced in the service when writing (revoke the prior active row before inserting a new one).

### d. `permission_audit_logs` — permission-specific change log

Kept separate from the generic `audit_trail`; this table backs the SA audit viewer (§5).

| column | type | notes |
|---|---|---|
| `log_id` | BIGINT UNSIGNED, PK, AI | |
| `changed_by` | BIGINT UNSIGNED, FK → `users.user_id` | |
| `target_user_id` | BIGINT UNSIGNED NULL | set for `user_override` |
| `target_role_id` | BIGINT UNSIGNED NULL | set for `role_default` |
| `permission_id` | BIGINT UNSIGNED, FK → `permissions.permission_id` | |
| `old_value` | BOOLEAN NULL | NULL on first-ever set |
| `new_value` | BOOLEAN | |
| `change_type` | ENUM('role_default','user_override','user_override_clear') | `user_override_clear` marks a revert-to-default (added in migration `..._000005`) |
| `reason` | TEXT NULL | |
| `changed_at` | TIMESTAMP | |

## 2. Permission Resolution Logic

A single service, **`App\Support\PermissionResolver`**, with a thin `User::can($feature, $action)` wrapper.

```
canUser(userId, feature, action): bool
  permId = permissionId(feature, action)        // cached feature/action → id map
  if permId is null:        return false         // unknown permission → deny
  override = user_permission_overrides
               .where(user_id = userId, permission_id = permId)
               .whereNull(revoked_at)
               .first()
  if override != null:      return (bool) override.is_granted   // override wins
  rp = role_permissions
         .where(role_id = user.role_id, permission_id = permId)
         .first()
  return rp != null ? (bool) rp.is_granted : false              // deny by default
```

**Performance**
- The `(feature, action) → permission_id` map is cached (changes only on deploy/seed).
- Per-request memoization of resolved checks.
- `effectivePermissionsFor(userId): array` loads the user's role defaults + active overrides in **two queries** and merges them — used for the frontend permission bootstrap and to gate many UI buttons without N queries.

## 3. Laravel Implementation Approach → **Combination: Middleware (b) + Gate/helper (a). No Policies.**

The codebase has no Gates/Policies and enforces exclusively through the variadic `role:` middleware, so we stay idiomatic:

- **(b) `permission:` middleware → `App\Http\Middleware\CheckPermission`** — signature `permission:feature,action`, mirroring `CheckRole` exactly. Registered as an alias beside `role`, `auditor.readonly`, etc. in `bootstrap/app.php`. **This is the Phase-2 route-enforcement vehicle.**
- **(a) Gate + `User::can($feature, $action)` helper** — for in-controller / in-React-bootstrap checks where one endpoint spans multiple actions.
- **Not Policies** — there is no existing policy layer, and permissions are feature/action-keyed (not model-keyed), so policies would add a parallel concept for no gain.
- **`auditor.readonly` stays** as the global outer guard — stricter than any grant, so an accidental auditor write-grant can never take effect (this is what makes Theme A safe).

## 4. Permission Management UI (SA only)

**Backend** — new `App\Http\Controllers\Api\PermissionController` under a `role:admin` group:

| method + path | purpose |
|---|---|
| `GET /permissions` | catalog (grouped by the 12 feature groups) |
| `GET /role-permissions` | full role × permission default grid |
| `PUT /role-permissions` | update one/many role default cells |
| `GET /users/{user}/permissions` | a user's effective perms (role default + active overrides) |
| `PUT /users/{user}/permissions` | set/clear overrides for a user |
| `GET /permission-audit-logs` | filterable audit feed (§5) |

Every write diffs old→new, persists, and writes a `permission_audit_logs` row in the same transaction.

**As-built safeguards (Task 7):** `updateRoleDefaults` validates `role_id` with `exists:roles,role_id` and **403s any attempt to edit the `admin` role's defaults**; `updateUserPermissions`/`userPermissions` **404** for an unknown `{userId}` and the write path **403s when the target user's role is `admin`** (admins cannot be locked out or have their permissions overridden). `auditLogs` validates all filter params (`nullable` integer/date/string). A user-override change with `is_granted: null` clears the override (writes a `user_override_clear` audit row).

**Page A — Role Permissions Editor** (replaces the stub `RolePermissions.jsx`):
A grid of features × actions, grouped by the 12 groups, with a toggle per role. Saving a cell updates `role_permissions` and writes a `role_default` audit row. Uses the existing `toast` + `confirm` helpers (`frontend/src/admin/utils/`).

**Page B — User Permission Overrides:**
SA selects a user → grid shows the role default as a greyed baseline, with any **active override highlighted**. Toggling a cell sets/clears an override. **A reason is required before save**; each change writes `user_permission_overrides` + a `user_override` audit row. "Reset to default" revokes the override.

## 5. Audit Log Viewer (SA only)

Read-only React page over `GET /permission-audit-logs`, filterable by **target user, role, feature, action, change_type, date range**. Columns: *changed-by · target (user or role) · feature · action · old → new · reason · timestamp*. The backend paginates and joins `permissions` + both user FKs for labels.
